The big picture

Raw doctor-patient chats arrive in two different shapes. The pipeline normalizes them (T3), explodes each chat into single-task training examples (T4), then pre-grades every example for quality and safety (T5) so human reviewers in T6 spend their time where it matters.

18,096 ACCEPT · 19,383 REVIEW · 8 REJECT (the red sliver is 0.02% — real, just tiny)

Rule of thumb for the whole store: every row carries its lineage (conversation_id, source_id, history[]), so any training example can be traced back to the exact raw chat it came from.

1

conversations.jsonl — one schema for two sources

conversations.jsonl · 41.7 MB · 9,518 rows · producer: T3 structuring/normalize.py

What

Each raw chat becomes one record: an id, a source tag, the turns rewritten as clean patient/doctor roles, plus meta and a history log of what T3 did.

Why

The two sources look nothing alike — Opus rows are ChatML with system turns and disease tags, iCliniq rows are forum Q&A. Every downstream script would need two code paths without this step. Normalizing once means everything after T3 speaks one dialect.

A real record: acne consultation, 26 turns (showing first 2)



Notice the history entry: “opus chatml; dropped 1 system turns; disease=Acne icd10=L70.0” — the normalize step narrates exactly what it changed, on the row itself.







2
quarantine.jsonl — the reject bin (empty on purpose)


quarantine.jsonl · 0 bytes · 0 rows · producer: T3




What
Conversations that fail validation go here instead of silently vanishing. Right now it is empty: all 9,518 chats passed.


Why keep an empty file?
Empty is a result, not an omission. The gate script hashes this file on every run (its SHA-256 is the well-known hash of an empty file), and the manifest asserts rows: 0. If a future data drop breaks parsing, failures land here visibly instead of corrupting the good store.









3
atomic.jsonl — chats exploded into single tasks


atomic.jsonl · 240.6 MB · 37,487 rows · producer: T4 curation/extract.py




What
Each conversation is split into atomic examples: one context + one user_message + one response, with an action label naming the task (answer, advise_professional_evaluation, …). Metadata starts life as triage: null — grading comes later.


Why
Models train on single tasks, not 26-turn sagas. One chat mixes greetings, history-taking, diagnosis, and prescriptions — grading or training on the whole blob would smear quality signals. Splitting gives 37,487 clean, independently gradable units, each still parent-linked via conversation_id.




Two children of the acne conversation above




See how the second example packs earlier turns into context? That keeps each example self-contained: a reviewer (or model) never needs to open the parent chat to understand it.






4
triaged.jsonl — every example pre-graded


triaged.jsonl · 265.9 MB · 37,487 rows · producer: T5 curation/triage.py (rules rules-triage/v1)




What
Same 37,487 rows as atomic.jsonl, except metadata.triage is now filled: a verdict, eleven 1–5 quality-dimension scores, a rule trace, and the grader version. Nothing else changes — the gate verifies that.


Why
37,487 rows is far more than humans can read. Deterministic rules pre-sort the pile: clean rows pass, suspicious rows queue for T6 human review, dangerous rows are rejected outright. Rules — not an LLM — because the harness demands byte-identical re-runs, and there is no network in the build sandbox.
